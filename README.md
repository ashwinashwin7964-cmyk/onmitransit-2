# OmniTransit-Agent Swarm

**Autonomous Multi-Agent Urban Digital Twin, 80/20 Machine Learning Estimation, Model Predictive Control (MPC), Robust Optimization Engine, Generative AI Causal Architect & Commercial Command Center**

> **[SIMULATION PLANNING SANDBOX MODE — POLICY EVALUATION ONLY]**
> All passenger demand, crowding load factors, and waiting-time comparisons generated by this platform are simulated policy projections calibrated on **2,000,000 synthetic transit telemetry records** and are strictly isolated from live passenger-facing arrival ETAs.

## 1. Problem Statement & Theme Alignment

### Problem Statement: Intelligent Public Transport Demand and Route Optimization
*Develop a data-driven system that estimates passenger demand, crowding, and waiting times across selected public transport routes using sample schedules, passenger counts, or simulated data. It should identify busy time periods, compare alternative routes, and recommend schedule or route adjustments that could reduce waiting and uneven demand. The prototype should explain why a route or timing is recommended and display estimated demand and waiting-time comparisons without presenting simulated estimates as live transport information.*

### Theme: AI, Generative AI & Autonomous Agents

OmniTransit addresses this challenge across the three required theme pillars:

1. **AI (Machine Learning & 80/20 Train/Test Validation):**
   - **80|20 Holdout Partition:** 2,000,000 synthetic commuter trips and 128 spatial-temporal smart blocks are strictly split into an 80% training set (1,634,470 rows / 102 blocks) and a 20% holdout test set (365,530 rows / 26 blocks).
   - **Gradient Boosted Decision Ensemble (LightGBM):** Evaluates non-linear passenger arrivals and headway delays across 8 arterial corridors in Coimbatore.
   - **Out-of-Sample Metrics:** Holdout Demand $R^2 = 0.8709$, Holdout Wait-Time $R^2 = 0.9595$, Holdout Wait-Time MAE $= 0.79$ minutes.

2. **Generative AI (Explainability & Causal Reasoning):**
   - **Causal AI Transit Architect:** Explains *why* schedule shifts and route adjustments are recommended under peak demand, monsoon cloudbursts, or corridor disruptions.
   - **Passenger Travel Advisories:** Synthesizes actionable B2C recommendations guiding commuters to alternative corridors and optimal departure windows to balance uneven demand.

3. **Autonomous Agents (Decentralized Multi-Agent Swarm):**
   - **Station Hub Agents (Buyers):** Monitor localized queuing and passenger distress; issue virtual token bounties when wait times exceed SLA thresholds ($>15.0$ mins).
   - **Route Fleet Agents (Sellers):** Audit vehicle load factors and negotiate bilateral token trades to dynamically reallocate underutilized fleet units to overloaded arterial routes.
   - **EV Grid & ESG Guardrails:** Audits State-of-Charge ($\text{SOC} \ge 25\%$) prior to vehicle transfer and mints Verified Carbon Credits (ESG offsets) for retained transit ridership.

## 3. Security: RFC 7519 JWT Authentication

All operational and administrative API endpoints are cryptographically protected via RFC 7519 JWT tokens signed with HMAC-SHA256:

- **Authentication Endpoint:** `POST /api/auth/login` validates credentials and issues a signed JWT token with a 24-hour expiration.
- **Verification Endpoint:** `POST /api/auth/verify` audits token signatures and role permissions.
- **Role-Based Access Control:**
  - `admin` (Chief Transit Architect): Full permissions (`TRAIN_MODEL`, `DISRUPT`, `OPTIMIZE`, `POLICY_OVERRIDE`).
  - `dispatcher` (Central Bus Dispatch Officer): `OPTIMIZE`, `VIEW_TELEMETRY`.
  - `planner` (Urban Mobility Research Lead): `TRAIN_MODEL`, `ROBUST_MPC_AUDIT`.
- **Protected Actions:** Model Retraining (`/api/train-model`), Adversarial Disruption (`/api/disrupt`), and Fleet Optimization (`/api/optimize`) require a valid `Bearer <token>` header.

## 4. Google Maps API & Spatial GIS Engine

- **Native Google Maps Integration:** High-resolution satellite, hybrid, and street views for Coimbatore Metropolitan Area (`11.025° N, 77.010° E`).
- **Secure Key Handling:** The Google Maps JavaScript API key is persisted securely on the backend in `data/app_config.json` and served via `/api/config`. The key string is masked in the UI and never exposed in plain text.
